# Minecraft Visual Design Foundations

## Purpose
Give the agent a design vocabulary and decision framework before it starts manipulating geometry or pixels.

## Trigger
Use before visual creation, during design critique, or when a user asks why an asset does not look professional.

## Inputs
Asset purpose, viewing distance, screen size, target style, reference, gameplay context and constraints.

## Workflow
1. Identify the primary message/function: what should the player recognize first?
2. Establish hierarchy: primary form, secondary feature, tertiary detail.
3. Check balance, proportion, rhythm, repetition, contrast, negative space and visual weight.
4. Check figure-ground separation against likely game backgrounds.
5. Use alignment and consistent spacing for icons, UI and modular asset families.
6. Remove details that do not improve recognition, material read or gameplay communication.
7. Test at native in-game scale and in a grayscale/value-only view.

## Design heuristics
- One dominant focal feature is usually stronger than many competing accents.
- Detail density should support the silhouette, not destroy it.
- Contrast is a limited resource; reserve the strongest contrast for the focal area.
- Repeated parts should share a measurable rhythm and spacing system.
- A visually attractive render is not automatically readable in gameplay.

## Outputs
Design analysis, hierarchy map, proportion/spacing notes, prioritized revisions and acceptance criteria.

## Safety
Do not alter the user's established brand/style system without explaining the change. Keep source files intact.

## Failure handling
If visual purpose or viewing scale is unknown, state assumptions and request only the missing detail that changes the design.

## Acceptance criteria
The asset is recognizable at intended size, has a clear focal hierarchy, separates from its background, and contains no unjustified detail.
